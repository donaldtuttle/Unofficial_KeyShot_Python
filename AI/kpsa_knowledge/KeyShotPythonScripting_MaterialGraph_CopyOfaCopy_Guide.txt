# Copy of a Copy: KeyShot Material Graph Duplication and Connection Integrity

## Overview

Copying a KeyShot material involves more than reproducing its name or list of nodes. Material Graphs are connected structures: textures, shaders, materials, and other nodes have parameter values and edges that determine how the material behaves.

The **Copy of a Copy** workflow grew out of a working, KeyShot-tested scripting reference. It addresses material duplication and graph reconstruction, including Multi-Materials and submaterials. A crucial part of the approach is explicitly **checking node and edge relationships** rather than assuming that successful creation of the copied nodes guarantees a correct graph.

This guide explains the graph-identity problem and the relevant KeyShot Python API. The original v1.3.6 example is retained [unchanged in the historical archive](archive/KeyShotPythonScripting_MaterialGraph_CopyOfaCopy_Guide_v1.3.6_HISTORICAL.txt). The archive documents an earlier implementation; it is not a substitute for testing a script against a specific KeyShot build and scene.

## Why identity matters

Materials and shader nodes can have the same name, and some shader nodes may have no meaningful name. Names alone therefore cannot reliably distinguish graph elements.

KeyShot assigns IDs to graph nodes and edges. IDs are useful when resolving actual graph instances during a running session, but **IDs should not be treated as persistent identities across a save-and-reopen cycle**. An ID that identifies a node before reopening a scene might not identify the same node afterward.

A robust graph-copy operation therefore distinguishes:

- **Names:** user-facing labels that can be empty or duplicated.
- **Runtime IDs:** identifiers useful for locating an actual node or edge in the current graph/session.
- **Graph structure:** node types, parameter values, input sockets, and edges connecting the actual source and target nodes.
- **Multi-Material membership:** the ordered submaterials and their own material roots/graphs.

A copied graph can contain the expected number of nodes and still be wrong if an edge points to the wrong node or target input.

## Copying and verification are separate operations

A duplication workflow may use KeyShot's built-in material-copy functionality and additional explicit graph operations. The built-in operation and the manual passes serve different purposes.

1. **Obtain the source material and graph.** Identify the intended material, Multi-Material, and submaterial roots.
2. **Create or locate the destination material.** Use the supported material API for the target version.
3. **Resolve node identities.** Match actual source and destination nodes without relying solely on their display names.
4. **Reconstruct or reconcile relationships as needed.** Parameters and directed edges matter, including the *specific destination parameter* to which an edge connects.
5. **Independently inspect the destination graph.** Verify what was created, rather than treating a successful creation call as proof that every connection is correct.
6. **Check persistence when relevant.** Save a test copy, reopen it, and re-identify graph instances before comparing connectivity. Do not compare old and new runtime ID values as if they were permanent keys.

**An additional manual connection pass is not inherently redundant.** In workflows with duplicate or unnamed nodes, checking the actual endpoints and inputs can be the part that establishes graph integrity. The necessity and implementation of each pass depend on the concrete source and target graphs.

### Example of the failure mode

Two texture nodes may both be called `Texture`, yet connect to different inputs of a shader. Matching by the string `"Texture"` could reconnect both inputs to the same node, even though the copied graph appears to contain all the expected nodes.

Correct reconstruction must distinguish the two instances and their separate directed connections.

## Relevant KeyShot Python API

The following API members are present in the repository's [captured KeyShot Studio 2026.3 beta `help(lux)` reference](../../lux/KeyShot_lux_API.md). These entries establish **documented availability and meaning for that recorded build**, not a fresh runtime test of every use case.

| API member | Documented role |
| --- | --- |
| `lux.createMultiMaterial(name=..., mat=...)` | Create a Multi-Material based on an existing material |
| `lux.getMaterialGraph(name=...)` | Retrieve a material's `MaterialGraph` |
| `lux.getMultiMaterial(name=...)` | Retrieve a `MultiMaterial` object |
| `MaterialGraph.getNodes()` | Retrieve the graph's nodes, independently of the edges |
| `MaterialGraph.getMaterialNodes()` | Retrieve material root nodes, including submaterial roots for a Multi-Material |
| `MaterialGraph.getNodeFromID(id=...)` | Resolve a node by its ID in that graph |
| `MaterialGraph.newNode(type=...)` | Create a shader node of the specified shader type |
| `MaterialGraph.newEdge(source=..., target=..., param=...)` | Connect a source node to a **specified parameter of the target node** |
| `ShaderNode.getID()` / `ShaderNode.getName()` | Retrieve a node's runtime ID and display name |
| `ShaderNode.getInputEdge(parameter=...)` | Retrieve the edge connected to a named input parameter |
| `ShaderNode.getInputEdges()` / `getOutputEdges()` | Inspect incoming and outgoing graph connections |
| `ShaderEdge.getID()` | Retrieve the **edge ID**, not the target parameter name |
| `ShaderEdge.getSourceNode()` / `getTargetNode()` | Retrieve the actual connected node instances |
| `ShaderNode.getParameters()` / `getParameter(name=...)` | Inspect parameters of a node |
| `ShaderParameter.getName()` / `isPure()` | Retrieve a parameter name and distinguish a pure parameter from one with a concrete value |
| `MultiMaterial.getSubMaterials()` / `setSubMaterials(mats=...)` | Read and set an **ordered** list of submaterials |

### Common API interpretation errors

**Edge ID is not the target input.** The `param` argument of `MaterialGraph.newEdge()` identifies a parameter **on the target node**. Substituting `ShaderEdge.getID()` does not establish the correct target input. When necessary, inspect the destination node's named input edges to determine which parameter carries an original connection.

**A parameter name is not a parameter ID.** In the captured API, `ShaderParameter` exposes `getName()`, `getType()`, `getValue()`, `isPure()`, and `setValue()`; it does not list a `getID()` method.

**Not every parameter has a concrete value.** The API explicitly documents that `isPure()` parameters cannot be read or written using `getValue()` and `setValue()`. Parameter copying must account for that distinction and for type-specific values.

**Shader types need the correct representation.** The API describes `ShaderNode.getType()` in terms of a shader type name and a human-friendly name, whereas `MaterialGraph.newNode()` requires a shader type. The correct value to pass must be established for the target KeyShot build instead of assuming those return and input representations are interchangeable.

**Material cloning is not a universal guarantee of graph equivalence.** The captured API documents how to create a Multi-Material from an existing material. It does not by itself prove that every node parameter, external texture reference, submaterial relationship, and connection was preserved for every source scene. Inspect the result.

## Checking a copied graph

A meaningful integrity check compares properties that make the graph behave correctly:

- Number and type of nodes in each relevant material/submaterial graph
- Concrete parameter names, types, and values where readable
- Directed edge endpoints and their **target input parameter names**
- Root and submaterial structure, including ordering
- Duplicate-name and unnamed-node scenarios
- Persistence after saving and reopening a test copy
- Rendered appearance, if appearance is part of the requirement

When comparing across sessions, use fresh node/edge IDs to traverse **each** graph, then compare the resolved structural relationships. Do not assume that two nodes are equivalent just because their display names or numeric IDs match.

A successful mock test or static Python check is not equivalent to executing the workflow in KeyShot. For guidance on static checks, mocks, and actual execution, see the repository's [AI constraints](../constraints.md), particularly the test-evidence requirements.
